# proxy-api для amoCRM

Ниже приведено техническое задание проекта. Проект реализован: структура,
конфигурация и поведение соответствуют разделам ниже. Инструкция по локальному
запуску и тестированию — в разделе [13](#13-локальный-запуск-и-тестирование).

## 1. Цель

Разработать минимальный HTTP-прокси на Go между клиентом и API amoCRM. Сервис
должен запускаться в Yandex Serverless Containers, ограничивать исходящий поток
до **5 запросов в секунду** и завершать каждый запрос максимум за **1 секунду**.

## 2. Объём работ

В рамках задачи необходимо:

- принять HTTP-запрос от клиента;
- проверить обязательные параметры и авторизацию;
- ограничить частоту запросов;
- проксировать запрос в API amoCRM;
- вернуть клиенту статус, заголовки и тело ответа amoCRM;
- корректно обрабатывать таймауты, ошибки сети и ответы `429`;
- подготовить контейнер и конфигурацию для Yandex Serverless Containers.

Необходимо исключить из первой версии:

- бизнес-логику amoCRM;
- хранение данных и локальную базу;
- пользовательские аккаунты и отдельный сервис авторизации;
- фоновые задачи и очереди;
- тесты.

## 3. Технологические требования

- Язык: Go, актуальная стабильная версия.
- Входящий транспорт: HTTP/1.1 или HTTP/2 через `net/http`.
- Исходящие REST-запросы к amoCRM: `resty`.
- Развёртывание: Yandex Cloud Serverless Containers.
- Образ: минимальный multi-stage Docker image.
- Основные зависимости: `resty` для REST-клиента и `zerolog` для структурированных
  логов.
- Конфигурация: переменные окружения, без секретов в исходном коде.
- Логи: `zerolog` в JSON-формате в `stdout`/`stderr`.
- Комментарии в коде: только короткие комментарии для неочевидной логики.

## 4. Контракт прокси

### 4.1. Endpoint

`ANY /{subdomain}/{path...}`

Прокси принимает методы `GET`, `POST`, `PUT`, `PATCH` и `DELETE`. Первый сегмент
пути — логический `subdomain`, остальные сегменты передаются в API amoCRM.
Значение `subdomain` нельзя использовать напрямую для формирования URL.

Пример:

```text
POST /client-a/api/v4/contacts
```

Прокси находит в Yandex Lockbox значение, связанное с `client-a`, получает из
него реальный subdomain amoCRM и формирует запрос:

```text
https://{subdomain из Lockbox}.amocrm.ru/api/v4/contacts
```

Строка запроса (`query string`) и тело запроса передаются без изменений.

Если subdomain не найден в разрешённом списке или соответствующее значение
отсутствует в Lockbox, сервис возвращает `404` и не выполняет запрос к amoCRM.

### 4.2. Авторизация и заголовки

Прокси требует от клиента заголовок `Authorization: Bearer <JWT>`. JWT
проверяется до обращения к Lockbox и amoCRM. После успешной проверки прокси
добавляет к запросу amoCRM внутренний заголовок `Authorization` со значением
`token` из записи subdomain в Lockbox.

Прокси также:

- передаёт `Content-Type`, `Accept` и `X-Request-ID`;
- не передаёт клиентские `Host`, `Content-Length` и hop-by-hop заголовки;
- не раскрывает JWT и токен amoCRM в ответах и логах.

Если `X-Request-ID` не передан, сервис генерирует короткий идентификатор запроса.

### 4.3. Ответы

Успешный ответ amoCRM возвращается клиенту с исходным HTTP-статусом и телом.
Заголовки копируются с фильтрацией hop-by-hop заголовков.

Ошибки самого прокси возвращаются в JSON:

```json
{
  "error": "request_timeout",
  "request_id": "..."
}
```

Минимальные статусы:

- `400` — некорректный путь или параметры;
- `401` — отсутствует, просрочен или некорректен JWT;
- `403` — JWT действителен, но не разрешает доступ к указанному subdomain;
- `429` — превышен лимит 5 RPS;
- `502` — ошибка соединения с amoCRM;
- `504` — превышен таймаут 1 секунда;
- `500` — внутренняя ошибка прокси.

## 5. Ограничение RPS

Требуется ограничивать исходящие запросы к amoCRM согласно полю `rps` выбранного
subdomain. Для значения `rps: 5` лимит составляет **5 запросов в секунду на
экземпляр контейнера**.

Правила:

- использовать один потокобезопасный limiter на экземпляр приложения;
- запрос, не получивший разрешение в течение доступного времени, завершать
  ответом `429`;
- не ставить запросы в неограниченную очередь;
- значение лимита брать из Lockbox для каждого subdomain;
- если `rps` отсутствует или меньше `1`, конфигурация subdomain считается
  некорректной и запросы к нему не выполняются;
- при масштабировании Yandex Containers лимит применяется отдельно к каждому
  экземпляру; для общего глобального лимита требуется отдельный внешний
  распределённый limiter и он не входит в первую версию.

## 6. Таймауты

Общий бюджет обработки одного запроса — **1 секунда** от начала обработки до
формирования ответа.

Требования:

- значение задавать через `REQUEST_TIMEOUT`, по умолчанию `1s`;
- применять `context.WithTimeout` ко всему запросу;
- использовать HTTP-клиент с тем же контекстом;
- выполнять исходящий запрос через `resty`, передавая ему контекст входящего
  запроса;
- не оставлять активные запросы после отмены контекста;
- при истечении бюджета возвращать `504`;
- таймауты подключения, чтения и ожидания заголовков не должны обходить общий
  таймаут.

Для `resty` отключить debug-режим в production (`RESTY_DEBUG=false`) и не
включать автоматическое логирование заголовков или тела ответа.

## 7. Декомпозиция компонентов

Минимальная структура проекта:

```text
cmd/proxy/main.go             # запуск HTTP-сервера
internal/config/config.go    # конфигурация из окружения
internal/auth/jwt.go         # проверка JWT клиента
internal/handler/proxy.go    # HTTP-вход и HTTP-ответ
internal/limiter/limiter.go  # ограничение RPS
internal/client/amocrm.go    # REST-запрос к amoCRM через resty
internal/httpx/headers.go    # фильтрация заголовков
internal/logging/logging.go # настройка zerolog
Dockerfile
README.md
```

Ответственность компонентов:

- `config` — загрузка, валидация и значения по умолчанию;
- `auth` — проверка подписи и claims JWT;
- `handler` — маршрутизация, контекст, коды ошибок и передача тела;
- `limiter` — ограничение частоты без бесконечной очереди;
- `client` — сборка и выполнение запроса к amoCRM через `resty`;
- `httpx` — безопасное копирование заголовков;
- `logging` — настройка `zerolog`, полей и уровней логирования;
- `main` — сборка зависимостей и запуск сервера.

## 8. Конфигурация

Обязательные переменные:

- `LOCKBOX_SECRET_ID` — идентификатор секрета Yandex Lockbox с JSON-конфигурацией;
- `JWT_PUBLIC_KEY` — публичный ключ для проверки подписи JWT в формате PEM;
- `JWT_ISSUER` — ожидаемое значение claim `iss`;
- `JWT_AUDIENCE` — ожидаемое значение claim `aud`.

Необязательные переменные:

- `REQUEST_TIMEOUT=1s`;
- `PORT=8080`;
- `LOG_LEVEL=info`;
- `RESTY_DEBUG=false`.

При отсутствии обязательной переменной контейнер должен завершаться с понятной
ошибкой в логах.

Для локального запуска в VS Code используется конфигурация
[`.vscode/launch.json`](/home/mangus/cloudetest/.vscode/launch.json) и файл
[`.env.debug`](/home/mangus/cloudetest/.env.debug). В debug-профиле применяются
локальный Lockbox-файл и демонстрационный RSA public key; реальные токены в него
добавлять нельзя.

### 8.1. Проверка JWT

Поддержать только заранее выбранный асимметричный алгоритм (например, `RS256`);
алгоритм брать из конфигурации и не принимать `none` или неожиданные алгоритмы.
Проверять подпись, `exp`, `nbf`, `iss` и `aud`. Просроченный, неподписанный или
неподходящий по claims токен отклонять с ответом `401`.

Для доступа к subdomain JWT должен содержать claim `subdomain` со значением,
совпадающим с первым сегментом URL. При отсутствии claim или несовпадении
возвращать `403`. Секреты для подписи JWT не хранить в репозитории.

### 8.2. Формат секрета Lockbox

Lockbox содержит JSON-объект. Ключ верхнего уровня — логический `subdomain`,
значения `token` и `rps` используются для обращения к amoCRM:

```json
{
  "client-a": {
    "token": "Bearer <amo_access_token>",
    "rps": 5
  },
  "client-b": {
    "token": "Bearer <amo_access_token>",
    "rps": 5
  }
}
```

Прокси должен:

- найти объект по subdomain из первого сегмента URL;
- проверить наличие непустого `token` и положительного числового `rps`;
- использовать `token` как готовое значение заголовка `Authorization`;
- создать отдельный limiter для каждого subdomain;
- кэшировать распарсенный JSON только в памяти;
- не записывать содержимое Lockbox в логи.

## 9. Безопасность

- разрешать только URL на основе subdomain, полученного из Lockbox;
- исключить открытый proxy и не использовать пользовательский subdomain как
  произвольный host;
- проверять JWT до применения limiter и до чтения токенов amoCRM;
- принимать только разрешённый алгоритм подписи JWT;
- не допускать подмену схемы, хоста и базового URL через входной путь;
- не логировать токены, тела запросов и персональные данные;
- ограничить размер входного тела разумным значением конфигурации;
- передавать только необходимые заголовки;
- использовать HTTPS для сформированного URL amoCRM.

## 10. Yandex Serverless Containers

Подготовить:

- `Dockerfile` с multi-stage сборкой и минимальным runtime-образом;
- запуск приложения на `0.0.0.0:$PORT`;
- health endpoint `GET /health`, возвращающий `200 OK`;
- настройки контейнера для доступа к Yandex Lockbox и передачи идентификатора
  секрета;
- минимальные CPU и RAM, достаточные для HTTP-прокси;
- ограничение максимального числа параллельных запросов согласно лимиту amoCRM.

JSON-конфигурация subdomain, включая `token`, должна передаваться через Yandex
Lockbox или механизм секретов Yandex Cloud, а не храниться в репозитории. При старте
контейнер загружает секрет и кэширует его только в памяти. При ошибке доступа к
Lockbox контейнер не должен обслуживать proxy-запросы.

В минимальном контейнере без SDK Lockbox JSON передаётся через
`LOCKBOX_SECRET_JSON` либо `LOCKBOX_SECRET_FILE` (путь к mounted-файлу). Эти
переменные являются практичным адаптером для Serverless Containers; обязательный
`LOCKBOX_SECRET_ID` сохраняется как идентификатор/метаданные секрета. Поле `subdomain` в записи
необязательно и по умолчанию равно ключу записи:
`{"client-a":{"subdomain":"real-account","token":"...","rps":5}}`.

## 11. Наблюдаемость

Использовать `zerolog` как единственный прикладной логгер. Настроить
JSON-вывод в `stdout`/`stderr`, уровень через `LOG_LEVEL` и единый формат
полей для входящих и исходящих запросов. Для запросов, выполняемых через
`resty`, логировать событие после получения ответа или ошибки.

Для каждого запроса логировать только:

- `request_id`;
- HTTP-метод и безопасный путь;
- `subdomain`;
- статус ответа;
- длительность;
- тип ошибки, если запрос завершился ошибкой.

Для исходящего запроса через `resty` дополнительно логировать безопасные
метаданные: HTTP-метод, URL без токенов и тела, статус и длительность. Не
логировать заголовки `Authorization`, содержимое Lockbox, JWT, тела запросов и
ответов.

Добавить корректное завершение по `SIGTERM` с ожиданием завершения активных
запросов в пределах таймаута контейнера.

## 12. Критерии приёмки

- контейнер собирается одной стандартной командой Docker;
- сервис запускается в Yandex Serverless Containers;
- `GET /health` возвращает `200`;
- запрос без JWT, с неверной подписью или просроченным JWT получает `401`;
- JWT с корректной подписью, но недопустимым subdomain получает `403`;
- запросы `/{subdomain}/*` доходят до amoCRM с Bearer-токеном из Lockbox;
- лимит каждого subdomain соответствует его полю `rps` (для `rps: 5` — не более
  5 исходящих запросов в секунду на экземпляр);
- запросы, ожидающие limiter, получают `429`, а не накапливаются бесконечно;
- любой запрос завершается не позднее 1 секунды с ответом `504` при превышении;
- ошибки amoCRM и сетевые ошибки возвращаются без раскрытия секретов;
- все прикладные логи формируются через `zerolog`;
- запросы к amoCRM выполняются через `resty`;
- разные логические subdomain используют соответствующие значения из Lockbox;
- неизвестный subdomain не приводит к запросу на произвольный host;
- в репозитории отсутствуют токены и другие секреты;
- автоматические тесты в рамках задачи не добавляются.

## 13. Локальный запуск и тестирование

### 13.1. Структура репозитория

```text
cmd/proxy/main.go            # точка входа, HTTP-сервер, graceful shutdown
internal/config/config.go    # переменные окружения, парсинг Lockbox JSON
internal/auth/jwt.go         # проверка RS256 JWT и claim subdomain
internal/handler/proxy.go    # маршрутизация, /health, коды ошибок, логирование
internal/limiter/limiter.go  # ограничение RPS на subdomain
internal/client/amocrm.go    # REST-запрос к amoCRM через resty
internal/httpx/headers.go    # фильтрация hop-by-hop заголовков
internal/logging/logging.go  # инициализация zerolog
Dockerfile                   # multi-stage образ для Yandex Serverless Containers
go.mod / go.sum               # зависимости (resty, jwt/v5, zerolog)
.env.debug                    # переменные окружения для локального запуска
.env.lockbox.debug            # локальный Lockbox JSON (только для разработки)
.jwt-private.debug.pem         # приватный ключ для генерации тестовых JWT (не для продакшена)
.jwt-public.debug.pem          # публичный ключ, соответствующий JWT_PUBLIC_KEY_FILE
.vscode/launch.json            # запуск проекта из VS Code с .env.debug
test.sh                        # curl-запрос к /api/v4/account через прокси
test.highload.sh               # серия параллельных запросов для проверки лимита RPS
```

### 13.2. Запуск локально

Собрать и запустить бинарник с переменными из `.env.debug`:

```bash
go build -o /tmp/proxy ./cmd/proxy
set -a && source .env.debug && set +a && /tmp/proxy
```

Либо запустить конфигурацию **Run proxy (debug)** из `.vscode/launch.json` в VS Code.

Проверка доступности:

```bash
curl -sS http://localhost:8080/health
```

### 13.3. Тестовые скрипты

`test.sh` подписывает одноразовый JWT приватным ключом `.jwt-private.debug.pem`
и отправляет один запрос к `/timconsult/api/v4/account`:

```bash
./test.sh
```

`test.highload.sh` отправляет несколько запросов параллельно и показывает
распределение статусов `200`/`429`, наглядно демонстрируя ограничение RPS
из Lockbox-конфигурации:

```bash
TOTAL_REQUESTS=50 CONCURRENCY=20 ./test.highload.sh
```

Приватный ключ и Lockbox-файл из `.env.debug` предназначены только для
локальной разработки; в продакшене используются реальные значения
`JWT_PUBLIC_KEY`/`JWT_PUBLIC_KEY_FILE` и `LOCKBOX_SECRET_JSON`/`LOCKBOX_SECRET_FILE`.

### 13.4. Проверка сборки

```bash
go test ./...
```

Тесты в проекте не добавлялись; команда используется только как проверка
компиляции всех пакетов.
